## 0. THE ONE LESSON THAT MATTERS (read first)

**The QA harness (`scripts/qa/mock-supabase.mjs`) serves FAKE data** — 60 rows named
"Test Company N", one funnel called "Default". It does **not** look like the real app.
Verifying UI against it will pass while the real screen is a mess. This burned a whole
sub-session: the "bulletproofing" was green while the user's live Leads page was full of
junk the harness never showed.

**To see what the user sees, do ONE of these before judging any UI:**
1. Pull real rows from Supabase (read-only) and feed them into a harness variant, **or**
2. Ask the user for a screenshot (the sandbox cannot reach `directksab2b.com` or
   `*.supabase.co`; images read perfectly).

Never claim a page is "clean/verified" from the mock harness alone again.

## 7. How to work here safely (recap)

- **Verify against REAL data or a screenshot**, never the mock harness alone (§0).
- Data changes: **snapshot first**, change `is_client` AND `raw.isClient` together, keep a
  one-line undo. Live tool the team uses — reversible beats clever.
- Code changes: append a self-contained `try/catch` `<script>` layer at the end of
  `index.html`; don't restructure the middle. Deploy = push dev + fast-forward
  `claude/new-session-9fhlp1`; verify the Vercel deployment goes READY.
- One clear next step at a time; the user is not a developer and has hit many dead ends —
  bias to reducing his workload and keeping everything reversible.
